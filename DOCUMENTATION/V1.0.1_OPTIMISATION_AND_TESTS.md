# V1.0.1 optimisation and validation

## Result and scope

The accepted input was the supplied v1.0.0 release, whose normal and diagnostic ROMs match the M66 anti-farming package byte for byte. This release preserves that scoring, saves and graphics-reuse baseline. It does not revert to M12R2 or reintroduce M16 speed modes.

With sound ON, the final diagnostic completes the same 300 updates about 8% faster in levels 1/5 and about 5% faster in levels 2/4 in NGPCraft's silicon timing model. Level 3 is unchanged. These gains are real within this controlled emulator comparison, but are modest. A major speed leap, a global optimisation maximum, full-game equivalence and physical-console speed have not been established. Further large gains likely require deeper changes to scene/gameplay processing and fresh equivalence proofs; they are not promised by this release.

## Exact ROMs

- normal: `Batman_V1.0.1.ngc`, 4,194,304 bytes, SHA-256 `ee275d385af368f793dcdb1e4637db847e8730ed0a7fef01027cf6ea0f95afd2`.
- diagnostic: `Batman_V1.0.1_Diags.ngc`, 4,194,304 bytes, SHA-256 `6cb5f6906cac4cd34c6959bc2b9d01b3c973272a1b1ccf2393484e969b279ebc`.

## What changed and why

1. **Execute repeated platform rendering from RAM.** `video.c` groups platform residency, map writes, camera work, rope drawing and the platform render body in the existing `platform_scan` overlay. The ROM entry still waits for complete presentation and selects the same stage-specific renderer. This avoids cartridge-fetch overhead for hot code, while retaining identical graphics work. `cat_map_read` and guarded byte-map fast paths share this RAM section. Sparse cathedral map writes and slow fallbacks remain valid. The additional map helpers showed no extra 300-refresh cadence improvement in the sampled trial; no separate gain is claimed for them.
2. **Reclaim existing vehicle scratch space.** The 2,323-entry vehicle key table is renamed per mutually exclusive stage. Level 2 needs 622 distinct valid keys and level 4 needs 605. Each mapping is a bijection: no formerly different keys are merged, no formerly equal keys split, and the 65535 sentinel is retained. The lookup shrinks from 1,298 to 622 bytes, freeing 676 bytes. The 64 resident slots, allocation/eviction behaviour, prepared pixels and animation identities stay intact. `RenderWork` remains 6,568 bytes; save/game-state layouts do not grow.
3. **Run vehicle road and midpoint kernels in that RAM.** The linker gives the same hot loop instructions a stage-owned RAM destination in the reclaimed tail. The loader installs them only for levels 2/4. ROM wrappers and tables remain in ROM. Signed wrapping, projected edges, clipping, off-screen rows and marker masks are preserved. A targeted randomized test caught a missing explicit jump between the ROM wrapper and RAM body; the final source fixes that path and passes all 600 kernel cases.
4. **Add the requested credit.** The shared menu/endgame credits card includes NGPC High Score Management, Hardhat Warrior and WWW.NGPC-DEV.COM. Layout is checked at the actual 160×152 resolution. Music and cinematic timings are unchanged.
5. **Release/build integration.** Both final names, diagnostic heading, Windows converter RAM bounds, Linux builder bounds and ROM identities are updated. The root BAT launcher is present with real CRLF endings. The original compiler-runtime repair is preserved. The cleaned website JSON remains compatible with the unchanged BATMAN2 overall and BATMAN3 stage payloads; the BATMAN63/BATMAN65 checksum salts are protocol constants.

The staged investigation isolated the platform move first (about 8% in levels 1/5), then the vehicle road move (about 4% in 2/4), then the midpoint move (about 5% combined in 2/4). These are overlapping cumulative candidates, not additive gains. Full final tests use only the final hashes listed above. No speed multiplier, clock change, skipped gameplay, quality reduction, new frame-skipping policy or artificial timer acceleration was added.

## RAM, ROM and lifetime proof

The normal linked platform overlay is 3575 bytes within its enforced 3,720-byte window; native edge code is 370 bytes within 400; road/midpoint code is 670 bytes within 676. The road window has only 6 bytes spare, so any later edit must rerun the bounds checks. Diagnostic bounds also pass.

The platform overlay starts at `render_work + 2560`; vehicle edge code uses its existing region at `render_work + 4544`; vehicle road code uses `render_work + 5892`. These lifetimes are mutually exclusive by stage. The outer union remains 6,568 bytes. The native stack and audio windows are not borrowed. The linker/builders reject BSS/runtime overlap, oversized overlays, split/overlapping S-record load images and ROM collisions with save/BIOS sectors. Both ROMs ship with file offsets 0x1F0000–0x1FFFFF erased. The entire second 2 MiB ROM window is byte-identical to the baseline, retaining its audio/ending assets. See `MEMORY_AND_ASSET_CHECKS.json` and the matching normal/diagnostic maps and logs.

## Regression evidence and its limits

- **Exact checkpoints, sound ON and OFF:** all five stages, 300 updates each. At `_perf_after_step`, compare all 2,776 stage-work bytes, 70 Game bytes, translated data/address registers and flags. At `_perf_present`, compare full committed maps/palettes/nonresident patterns and every sprite's resolved pattern and normalized descriptor. This permits tile-identity remapping without masking visible artwork. All 3,000 states and all 3,000 committed surfaces match the unchanged baseline. These breakpoint runs prove equivalence at sampled update boundaries; the separate uninstrumented benchmark measures cadence.
- **Vehicle kernel boundary tests on normal ROMs:** 400 seeded road cases plus 200 midpoint cases compare complete outputs against the unchanged normal baseline. Inputs include all four outer-marker masks, inner-marker suppression, signed projected edges, zero/maximum row counts and partially/fully off-screen rows. The fixture installs the actual RAM load image and disables interrupts for the isolated call only. This is a kernel fixture, not a game-speed measurement.
- **Normal-ROM feature test:** real checkpoint banking, respawn/retry anti-farming, improvement-only points, actual flash save, cold-boot Continue, preserved eligibility, positive-score QR generation, zero-score upload blocking, persistent reset, full shared credits sequence and guard checks passed. Scores and death waits are injected at real game-tick breakpoints to exercise handlers reproducibly. This is explicitly not a naturally played campaign or website upload.
- **Host arithmetic test:** eight existing anti-farming tests passed. The actual QR payload generated by the normal ROM decodes with the independent validator and its CRC/formula checks; it is supplied in `features_final/actual_qr_payload.txt`. No score was submitted online.
- **Build:** Toshiba C/ASM/link/conversion passed for both current ROMs under the Linux compatibility runner. Matching build logs, maps and results are included. Native Windows was unavailable here, so the BAT/PowerShell build is included and reviewed but not claimed as executed on Windows. Historical Windows/MAME evidence elsewhere in the archive applies to its labelled older versions.

Coverage is the fixed first 300 gameplay updates of each diagnostic route, the specified edge fixtures and feature handlers. It cannot prove every later scene or physical-console timing. Use the supplied hardware checklist and normal-ROM playtesting before declaring a hardware final.

## Reproduce

Build both ROMs using the root README. The following native-core build was used on x86-64 Linux with Python 3 and g++:

```sh
git clone https://github.com/Tixul/Ngpcraft_emulator.git ngpcraft_emulator
git -C ngpcraft_emulator checkout c769b511dc54f4d72f22d4699cfbb5cd68aa14a2
cd ngpcraft_emulator
mkdir -p cpp/build
g++ -std=c++17 -O3 -DNDEBUG -fPIC -shared -Icpp/include -Icpp/src cpp/src/core.cpp cpp/src/memory.cpp cpp/src/execute.cpp cpp/src/mem_family.cpp cpp/src/reg_family.cpp cpp/src/z80.cpp cpp/src/apu.cpp cpp/src/render.cpp -o cpp/build/ngpc_core.so
cd ..
```

From the extracted release directory, replace `/absolute/path/ngpcraft_emulator` below with that checkout. The HLE BIOS comes from its `hle_bios/bios_hle.bin`. No commercial BIOS is redistributed in this package.

```sh
python3 SOURCE/tools/bench_ngpcraft.py --emulator /absolute/path/ngpcraft_emulator --rom OUTPUT/Batman_V1.0.1_Diags.ngc --map EVIDENCE/V101_DIAGNOSTIC_BUILD/batman.map --out trial-on.json --stages 1,2,3,4,5
python3 SOURCE/tools/capture_ngpcraft.py --emulator /absolute/path/ngpcraft_emulator --rom OUTPUT/Batman_V1.0.1_Diags.ngc --map EVIDENCE/V101_DIAGNOSTIC_BUILD/batman.map --out capture-new
python3 SOURCE/tools/capture_ngpcraft.py --emulator /absolute/path/ngpcraft_emulator --rom REFERENCE_V1.0.0/Batman_M66_Anti_Farming_Diagnostic_4MB.ngc --map REFERENCE_V1.0.0/diagnostic.map --out capture-old
python3 SOURCE/tools/compare_ngpcraft.py --baseline capture-old --candidate capture-new --out comparison.json
python3 SOURCE/tools/test_vehicle_kernels_ngpcraft.py --emulator /absolute/path/ngpcraft_emulator --baseline-rom REFERENCE_V1.0.0/Batman_M66_Anti_Farming_Normal_4MB.ngc --baseline-map REFERENCE_V1.0.0/normal.map --rom OUTPUT/Batman_V1.0.1.ngc --map EVIDENCE/V101_NORMAL_BUILD/batman.map --out kernels.json
python3 SOURCE/tools/test_features_ngpcraft.py --emulator /absolute/path/ngpcraft_emulator --rom OUTPUT/Batman_V1.0.1.ngc --map EVIDENCE/V101_NORMAL_BUILD/batman.map --out features
python3 SOURCE/tools/verify_v101_keys.py
python3 SOURCE/tools/test_anti_farming.py --output anti-farming.json
```

Repeat benchmark and capture commands with `--sound-off`. Run the benchmark on the baseline ROM/map as well. The feature fixture mutates only its emulator instance; it does not edit the release ROM file. The native kernel tests do not need a BIOS.

## Reusable optimisation guidance

The extensive `NGPC_PORT_OPTIMISATION_TEMPLATE.md` remains included. Add this lesson to a future port: measure cartridge instruction-fetch cost before rewriting game logic; compact cache identifiers only with a stage-lifetime and equality proof; relocate hot code only into demonstrably unused, stage-owned RAM; retain explicit control transfers across ROM/RAM section boundaries; test rare marker/clipping/flags independently of ordinary replay coverage. Never add individual percentage gains together. Publish final-hash results and compare on the same physical console before claiming a hardware win.
